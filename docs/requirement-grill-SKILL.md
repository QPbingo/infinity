# 需求澄清与验证 (Requirement Grill)

将用户模糊的自然语言需求，经过五维度动态拷问，转化为一份经过验证的、清晰无歧义的需求文档（Validation Brief）。

## 核心目标

**深挖用户到底想干什么，消除自然语言表达的歧义。** 这是本 skill 的北极星指标。每一轮追问都应服务于这个目标。

## 执行流程

### 第一步：解析与复述

收到用户需求后，用你自己的话复述你对需求的理解。目标是确认你没有理解偏，以及暴露用户表述中可能存在的模糊点。

复述格式：
> 我理解你的需求是：[一句话复述]
> 其中我注意到以下几个可能模糊的点：
> 1. [模糊点] — 我的理解是 [X]，对吗？
> 2. ...

等待用户确认或纠正后再进入下一步。

### 第二步：动态 Grill

这是核心阶段。AI 根据用户的回答**动态决定**下一步追问哪个维度，不按固定顺序执行。

#### 维度总览

| 维度 | 级别 | 绿灯条件 |
|------|------|----------|
| 必要性 | **必过** | 有证据支撑 / 不做的影响已明确 / 不是伪需求 |
| 一致性 | **必过** | 不与已有系统冲突 / 不与其它需求矛盾 |
| 边界 | **必过** | 范围明确 / 反场景已识别 / 极端输入已覆盖 |
| 优先级 | 弹性 | must/nice 已区分 / 最小可行方案已识别 |
| 成功标准 | 弹性 | 验收标准可检验 / 成功指标有基线 |

#### 必过维度 — 锚点问题

**必要性（Existential Grill）**
核心目标：排除 XY Problem——用户要的是方案 Y，但真正需要解决的是问题 X。

锚点问题（必须覆盖，但不一定逐字照念）：
- 这个需求要解决的痛苦或机会，有数据或具体证据吗？
- 如果不做，三个月后会有什么实际影响？
- 这是问题本身，还是你自己猜的解决方案？有没有更根本的问题？

**一致性（Consistency Grill）**
锚点问题：
- 这个需求和已有系统/之前的需求有没有矛盾？
- 项目现有的架构和技术约束下，这个需求兼容吗？
- 团队能力和时间约束下，现实吗？

**边界（Boundary Grill）**
锚点问题：
- 什么情况下这个需求反而是有害的或不必要的？
- 极端输入/最大数据量/并发边界在哪里？边界处系统应该怎样？
- 如果输入是空的、错的、恶意的，预期行为是什么？

#### 弹性维度 — 锚点问题

**优先级（Priority Grill）** — 需求涉及多个功能点时启用
锚点问题：
- 如果只能做一件事达到 80% 效果，你选哪件？
- 有没有更简单的方式达到同样目的？

**成功标准（Success Grill）** — 需求有上线计划时启用
锚点问题：
- 你怎么判断这个需求做完了？具体可检验的验收标准是什么？
- 上线后用什么指标判断它成功？这个指标现在有基线吗？
- 如果上线后没人用，最可能的原因是什么？

#### 路由策略

- **每个维度至少覆盖锚点问题**，但 AI 可以灵活措辞，不逐字照念
- 用户回答若已自然覆盖某维度，该维度可直接标记绿灯，无需机械追问
- 发现矛盾或新模糊点，可以回到之前的维度补充追问
- 锚点之外的追问由 AI 根据上下文动态生成，目标是深挖意图、消除歧义
- 弹性维度是否启用由 AI 判断：需求明显简单则跳过，用户也可主动要求启用/跳过

#### 追问原则

- **一次只问一个问题**，等用户回答后再继续
- **每个问题附带你的推荐答案**，降低用户回答成本
- **追问要具体**，避免「你能再详细说说吗？」这类泛问题
- **发现假设就确认**——「你这里隐含了一个假设是 X，这个假设对吗？」
- **用户说了一个词但可能有多种含义时，立刻确认**——「你说的『快』是指响应延迟 < 100ms，还是指开发周期短？」

### 第三步：歧义扫描

所有必过维度绿灯亮起后，做一次专门的歧义检查：

- 需求中还有没有多义词、模糊形容词（快、好、稳定、友好）？
- 有没有隐含的但未经确认的假设？
- 有没有用户觉得「显然」但你实际不确定的地方？

将任何残留模糊点列出来请用户最终确认。

### 第四步：产出 Validation Brief

按以下模板撰写，请用户确认：

```markdown
# 需求验证摘要

## 原始需求
[用户最初的一句话/一段话]

## 核心意图
[经 grill 后澄清的真正目标 —— 用户到底想干什么]
- 一句话核心目标：
- 消除的关键歧义：
  1. [模糊点] → [澄清后的理解]
  2. ...

## 维度摘要

### 必要性 ✅
- 要解决的痛苦/机会：
- 证据/数据支撑：
- 不做的后果：
- 判定：通过

### 一致性 ✅
- 与已有系统的关系：
- 与其它需求的兼容性：
- 已识别的潜在冲突及处理方式：
- 判定：通过

### 边界 ✅
- 明确在范围内：
- 明确不在范围内：
- 极端/异常场景及预期行为：
- 判定：通过

### 优先级 (如启用)
- must-have vs nice-to-have：
- 最小可行方案：
- 分阶段交付建议：

### 成功标准 (如启用)
- 验收标准（可检验）：
- 上线后成功指标及当前基线：
- 如果没人用的最可能原因：

## Grill 结论
- 状态：✅ 通过 / ⚠️ 有条件通过 / ❌ 需要重新定义
- 遗留的待验证假设：
- 建议的下一步：
```

### 第五步：落盘

用户确认 Brief 无误后，写入文件 `docs/requirement-briefs/<日期>-<需求简称>.md`。

## 退出机制

三层保障，确保既不遗漏也不过度追问：

1. **绿灯底线**：3 个必过维度的锚点问题必须全覆盖，防止遗漏
2. **信心阈值**：AI 判断对「用户真正想要什么」已有足够信心时，可提前收束某个维度，不必机械走完所有锚点
3. **用户叫停**：用户随时可以说「够了」「跳过这题」「直接出 Brief」，立刻跳到第四步

## 状态判定

- ✅ **通过**：3 必过维度绿灯全亮，核心意图清晰无歧义
- ⚠️ **有条件通过**：核心意图清晰，但有遗留假设需要在实际执行中验证
- ❌ **需要重新定义**：核心意图本身模糊或矛盾，建议用户回到问题原点重新思考

## 何时使用

- 用户提了一个模糊的需求，直接开始做之前
- 用户自己说「我想做个 X，但不太确定具体怎么做」
- 需求看起来简单，但感觉有隐含假设没被说清楚
- 多个人对同一个需求的理解不一致时
- 需求多次返工，发现一开始就没对齐时

## 何时不用

- 需求已经非常具体和清晰（有精确的验收标准）
- 用户只是问一个事实性问题，不是提需求
- 用户明确说「不用问了，直接做」

## 核心原则

- **北极星是消除歧义**：每一问都应该让「用户到底想要什么」变得更清晰
- **一次一问**：永远不要一次抛出多个问题
- **带推荐答案**：每个问题给出你的判断，用户只需确认或纠正
- **AI 动态路由**：不按死顺序，根据用户回答智能决定下一步
- **零外部依赖**：本 skill 自包含，不需要安装任何其他 skill
